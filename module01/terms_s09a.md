# Terms from Session 9a — what they are, and where they come back

Every new word introduced in Session 9a. The notebook (`s09a_first_call.ipynb`, Part A3) explains each one in full, with an example and the term it is most often confused with.

| Term | What it is | Say it as | Comes back at |
|---|---|---|---|
| Repository (repo): the course repo and your work repo | a project folder that Git tracks, with its full history. This course uses **two**, side by side in `Documents`: the **course repository** `adv-genai` (the instructor's; you only `git pull` it) and your **work repository** `adv-genai-work` (yours; you `git add`, `commit` and `push` your submissions to it, from Session 14). | a folder with a memory. The course repo is the textbook you photocopy and collect new pages for; the work repo is your own exercise book that you hand in. | S14 (your work repo), every session (`git pull`). |
| uv | a tool that installs Python versions, creates the project's environment and installs the project's packages. | the toolbox manager: it fetches the right tools and puts them in this project's box. | every session. |
| Virtual environment (`.venv`) | a folder inside the project that holds the project's own Python and its own packages. | the project's toolbox. Other projects have their own boxes; nobody borrows tools from yours. | every session. |
| `pyproject.toml` and the lock file `uv.lock` | `pyproject.toml` is the list of packages the project needs (with allowed version ranges); `uv.lock` pins the **exact** version of every package, including the packages those packages need. | the shopping list and the exact receipt. | S9b, and whenever packages are added. |
| `uv sync` and `uv run` | `uv sync` makes `.venv` match the lock file exactly. `uv run <command>` runs a command with the project's Python and packages (and syncs first if needed). | `uv sync` packs the toolbox from the receipt; `uv run` says "use the tools from *this* box". | every session. *The course rule: every Python command starts with `uv run`.* |
| Environment variable | a named setting (name = value) that a running program can read, for example with `os.getenv("MODEL")`. | a note stuck on the program's door before it starts work. | every lab; Module 12 (deployment). |
| `.env` and `.env.example` | `.env` is a small private text file of settings (`NAME=value` lines) that `load_dotenv` turns into environment variables. `.env.example` is the public template with placeholders. | `.env.example` is the blank form pinned on the notice board; `.env` is your locker. | every lab; S11 (Gemini key), S16 (`WORK_REPO`). |
| `.gitignore` | a list of files and folders Git must never track. The course repo lists `.env` (and `.venv`) in it. | "do not photocopy these". | S14 (your work repo gets its own `.gitignore`), every submission. |
| API and API key | an API is a way for one program to ask another program, over the internet, to do something. An **API key** is your secret credential for that service. | the key is your ATM PIN. The PIN is not the money, but it lets somebody else spend it. | S11 (a second key), S55–S57 (security). |
| `BASE_URL`, `API_KEY`, `MODEL`: the three settings | **where** the request goes, **who** is asking, and **which model** answers. | the address on the envelope, your signature, and the name of the expert you want to answer. | S10 (why `MODEL` is pinned), S11 (switching providers), S12 (Ollama). |
| Provider and OpenAI-compatible API | a **provider** is the company or server that runs the model (Groq, Ollama on your laptop, Gemini). **OpenAI-compatible** means it accepts the same request format as OpenAI's Chat Completions API, so one client library talks to all of them. | different banks' ATMs that all accept the same card. | S11, S12. |
| Client (client library) | a Python object, from the `openai` package, that knows how to send requests to a provider and turn the replies into Python objects. | the phone you dial with. Making the phone does not call anyone. | S11, and every lab after. |
| Messages and roles (system, user) | the request is a **list of messages**. Each has a **role** and **content**. **system** = who the model is and how it behaves; **user** = what was asked. (The model's reply has the role **assistant**.) | the system message is the job description you give a new employee; the user message is the customer at the counter. | S11, S14 (anatomy of a prompt), S19 (conversation history). |
| Streaming and chunks | with `stream=True` the reply arrives in many small pieces (**chunks**) while the model writes it, instead of all at once at the end. | watching a live cricket score update ball by ball, instead of reading the result in tomorrow's paper. | S11, S22 (serving), S53 (time to first token). |
| Tokens and usage (prompt, completion, total) | a **token** is the unit a model reads, writes and bills by (roughly three-quarters of an English word). **Usage** is the count the provider reports after a call: **prompt** tokens (what you sent, plus some the provider adds), **completion** tokens (what the model produced), **total**. | the bill, in tokens. | S9b, S15 (reasoning tokens), S19 (token budgets), S53 (cost per run). |
| Checkpoint test (pytest) | a small program that checks your work and reports `passed`, `failed` or `skipped`. | the examiner. Green, or you are not finished. | every session; S51 (evaluation-driven development). |
